01 · Project purpose

One reviewed contract. Consistent API checks.

oas-polycontract shows how a reviewed specification can guide provider verification, consumer development against a provider Smart Mock, and live API integration tests.

Reviewed contractsOne source per API boundary
→
Automated checksProvider and API integration
→
Consumer supportSmart Mock and debug views
One contract owner→Fewer duplicate specs→Lower maintenance cost
Removing duplicate specifications and overlapping tools can reduce maintenance and tooling costs. The sample covers one Product lookup and an in-memory Order lifecycle; it is a pilot template, not proof of enterprise-scale coverage. See the enterprise adoption notes and the README project map.
02 · Project structure

Separate contracts by API boundary.

The repository keeps the design scaffold, runnable services, downstream dependency, and event examples distinct. Each contract has a clear scope and corresponding checks.

Product CatalogRoot OAS scaffold

openapi/ holds a design example without a provider implementation. contracts/baselines/ keeps separate accepted snapshots for runnable providers.

Runnable APIsProduct and Order examples

demo/ contains one Product lookup, an in-memory Order lifecycle scoped to each app instance, and a WireMock-backed Inventory dependency.

Behavior testsGherkin acceptance and service unit tests

clients/js/features/ supplies Product and Order scenarios to Cucumber. Node.js service tests check those behaviors in isolation before pipeline gates run.

Events and evaluationsSeparate contract types and checks

contracts/events/ holds linted AsyncAPI examples. evals/ checks docs, test entry points, collection paths, pipeline wiring, mock cases, and roadmap progress.

Phase 5 · examples deliveredManual collection migration

legacy/ holds OAS-aligned Postman and Bruno examples for Product lookup and the stateful Order flow. Their paths are checked against the contracts.

Open the collections and setup guide

Contracts are read-only pipeline inputs. Change them through reviewed source updates; publish immutable versions for provider and consumer projects to pin. Event contracts are linted examples; no WebSocket server or Kafka broker is included.
03 · Pipeline

One command runs the demonstration.

Run bash ./run.sh locally or in Ubuntu CI. The Node.js Testcontainers runner checks repository wiring, runs contract gates, pulls pinned upstream runtimes, then starts services on a private network. OAS, fixtures, and client sources are read-only mounts; dependency and build output stays in temporary directories. Health checks gate API tests, and the runner removes containers and the network when the run ends.

Contract gatesLint and compatibility

Spectral checks OpenAPI and AsyncAPI; oasdiff checks the root contract against its baseline.

Container orchestrationTestcontainers for Node.js

Uses pinned upstream language runtimes, creates an isolated network, waits for service health, runs one-shot checks, and cleans up without publishing ports.

API integrationNative suites and Playwright

Language suites call the Product API at app:8080 and Order API at stateful-app:8082. See the framework box in the test-role map.

Repository evaluations→Service unit tests→Contract and API gates→BDD acceptance features→Trivy image scans
For a focused local run, set POLYCONTRACT_NATIVE_CLIENTS=rust,python. CI leaves it unset and runs all seven native suites.

06 · Test behavior

Test independent requests and linked workflows.

Stateless fuzzingOne request stands on its own

Schemathesis generates independent Product API requests from OAS, probes boundaries, and validates responses. Each case does not rely on data from earlier cases.

Stateful testingFollow linked operations

The separate Order API preserves state across a lifecycle. OAS links pass the created identifier between operations.

Create→Read→Confirm→Delete→Verify 404

Rust, Go, Python, JavaScript, TypeScript, Java, and C# repeat the lifecycle and validate each response against the stateful OAS.

07 · Native API tests

Validate live responses in native test suites.

Each example uses a small API client object for requests and a language-native test framework for behavior and OAS response validation.

Rust · Go · PythonNative HTTP clients

reqwest, net/http, and requests validate response status, media type, and schema.

JavaScript · TypeScriptNode test runner and Vitest

@oaverify/core validates live provider responses and Smart Mock examples.

Java · C#JUnit and xUnit

REST Assured and HttpClient cover live Product API and stateful Order API integration. Playwright covers the live Product API.

For manual exploration, optional Swagger UI and Prism views load the root contract. They serve a different role from the automated checks.

One reviewed contract. Consistent API checks.

02 · Project structure

Separate contracts by API boundary.

The repository keeps the design scaffold, runnable services, downstream dependency, and event examples distinct. Each contract has a clear scope and corresponding checks.

Product CatalogRoot OAS scaffold

openapi/ holds the hand-edited contract and compatibility baseline. It has no provider implementation.

Runnable APIsProduct and Order services

demo/ contains the Product API, isolated stateful Order API, and Inventory dependency backed by WireMock.

Events and clientsSeparate examples

AsyncAPI examples describe WebSocket and Kafka messages. clients/ holds native language tests.

The event contracts are linted examples. This project does not include a WebSocket server or Kafka broker.
03 · Pipeline

One command runs the demonstration.

Run bash ./run.sh locally or in Ubuntu CI. Compose starts the services, waits for health checks, executes the gates, and cleans up.

Contract gatesLint and compatibility

Spectral checks OpenAPI and AsyncAPI; oasdiff checks the root contract against its baseline.

Live servicesVerify and integrate

Specmatic, Schemathesis, seven language suites, and Playwright call the running APIs. WireMock serves inventory.

Security and consumersScan and mock

Image scans run in CI. JavaScript and Playwright consumer examples use the Specmatic Smart Mock.

Lint contracts→Start services→Run contract and API checks→Scan images
04 · Contract roles

Provider verification and consumer testing are distinct.

Both use the Product OAS, but target different systems and validate different responsibilities.

ProviderDoes the service meet its contract?

Specmatic sends contract-derived requests to the healthy Product API. Its downstream check validates the WireMock-backed Inventory dependency.

ConsumerCan the client use the agreed interface?

JavaScript and Playwright examples run against a Specmatic Smart Mock. Their API integration runs separately target the live service.

The consumer example uses a mock generated from the shared provider OAS; it does not include a separate consumer-owned CDC contract.
05 · Test behavior

Test independent requests and linked workflows.

Stateless fuzzingOne request stands on its own

Schemathesis generates independent Product API requests from OAS, probes boundaries, and validates responses. Each case does not rely on data from earlier cases.

Stateful testingFollow linked operations

The separate Order API preserves state across a lifecycle. OAS links pass the created identifier between operations.

Create→Read→Confirm→Delete→Verify 404

Seven native clients repeat the lifecycle and validate each live response against the stateful OAS.

06 · Native API tests

Validate live responses in native test suites.

Each example uses a small API client object for requests and a language-native test framework for behavior and OAS response validation.

Rust · Go · PythonNative HTTP clients

Typed request helpers, test fixtures, lifecycle checks, and contract validators.

JavaScript · TypeScriptCode-based suites

JavaScript test runner and TypeScript test runner validate live provider responses.

Java · C# · PlaywrightFramework-native tests

JUnit and xUnit cover the lifecycle; Playwright APIRequestContext demonstrates provider and consumer tests.

For manual exploration, optional Swagger UI and Prism views load the root contract. They serve a different role from the automated checks.

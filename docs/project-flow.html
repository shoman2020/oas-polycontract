01 · Project purpose

One reviewed contract. Consistent API checks.

oas-polycontract demonstrates an OpenAPI-first workflow: teams maintain the contract, then use it to validate providers, support consumer development, and check live APIs in code.

02 · Project structure

Separate contracts by API boundary.

The repository keeps the design scaffold, runnable services, downstream dependency, and event examples distinct. Each contract has a clear scope and corresponding checks.

Product CatalogRoot OAS scaffold

openapi/ holds the hand-edited contract and compatibility baseline. It has no provider implementation.

Runnable APIsProduct and Order services

demo/ contains the Product API, isolated stateful Order API, and Inventory dependency backed by WireMock.

Events, clients, evaluationsSeparate checks

contracts/events/ holds linted AsyncAPI examples; clients/ holds native suites; evals/ checks docs, test entry points, pipeline wiring, mock cases, and roadmap tracking.

The event contracts are linted examples. This project does not include a WebSocket server or Kafka broker.
03 · Pipeline

One command runs the demonstration.

Run bash ./run.sh locally or in Ubuntu CI. Compose validates its configuration and builds images, repository evaluations run before the contract gates, then Compose starts services, waits for health checks, and runs the API suites.

Contract gatesLint and compatibility

Spectral checks OpenAPI and AsyncAPI; oasdiff checks the root contract against its baseline.

Live servicesNode.js, WireMock, Specmatic

Schemathesis and the API integration suites exercise the running Product and Order APIs.

API integrationRust, Go, Python, JavaScript, TypeScript, Java, C#

The language suites call the Product API at app:8080 and Order API at stateful-app:8082. Playwright adds a live API integration example.

Compose config and build→Repository evals→Contract and API checks→Trivy image scans

05 · Contract roles

Contract tests and API integration tests have distinct targets.

Specmatic provider and consumer checks use the Product OAS with different targets. Native language suites exercise the live APIs.

Provider contract testSpecmatic → live Product API

Contract-derived requests go to the healthy app at app:8080. Specmatic verifies the provider responses against the shared OAS.

Consumer contract testJavaScript / Playwright → Smart Mock

Both examples call the Specmatic mock at specmatic-mock:9000, created from the Product OAS.

API integrationNative clients → live Product and Order APIs

Seven language suites and Playwright provider tests send real requests, validate response schemas, and check business behavior.

The consumer examples share the provider OAS; this project does not publish a separate consumer-owned CDC contract.
06 · Test behavior

Test independent requests and linked workflows.

Stateless fuzzingOne request stands on its own

Schemathesis generates independent Product API requests from OAS, probes boundaries, and validates responses. Each case does not rely on data from earlier cases.

Stateful testingFollow linked operations

The separate Order API preserves state across a lifecycle. OAS links pass the created identifier between operations.

Create→Read→Confirm→Delete→Verify 404

Rust, Go, Python, JavaScript, TypeScript, Java, and C# repeat the lifecycle and validate each response against the stateful OAS.

07 · Native API tests

Validate live responses in native test suites.

Each example uses a small API client object for requests and a language-native test framework for behavior and OAS response validation.

Rust · Go · PythonNative HTTP clients

reqwest, net/http, and requests validate response status, media type, and schema.

JavaScript · TypeScriptNode test runner and Vitest

@oaverify/core validates live provider responses and Smart Mock examples.

Java · C#JUnit and xUnit

REST Assured and HttpClient cover live Product API and stateful Order API integration. Playwright covers the live Product API.

For manual exploration, optional Swagger UI and Prism views load the root contract. They serve a different role from the automated checks.
